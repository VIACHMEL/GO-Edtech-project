# Django для представления, Go для логики

- Статус: принято по прямым указаниям владельца в текущем обсуждении.
- Дата: 2026-11-03.

## Проблема и варианты

Ранее был выбран Rust для интерфейса. Владелец запросил Django, отдельно потребовал сохранить логику на Go и поручил создать заготовку в frontend/.

Рассмотрены: Go + Rust; полная замена на Django; Django как представление поверх Go. Принят последний вариант.

## Решение

- backend/ остаётся Go: пользователи, права, предметные правила, постоянные данные и их миграции.
- frontend/ — Python/Django: обработчики страниц, шаблоны, оформление, клиент HTTP API Go.
- Django 5.2 LTS, точные версии в frontend/requirements.txt; Python 3.12–3.14.
- Django не подключается к предметной БД и не вводит свои модели пользователей, оценок и работ.
- Парсер Школково и SVG → TikZ остаются обязательными для MVP. Тяжёлая обработка отдельно от запросов страниц.

## Последствия и совместимость

Исходного кода Rust, Cargo.toml, Go API, БД и существующих пользовательских сеансов нет: перенос данных и миграция работающего приложения не требуются. Языки и команды проверки в документации обновляются. Публичные API Go не создаются этим решением.

Добавляются два процесса; необходимо согласовать API, ошибки, ограничения времени и механизм передачи личности. Django не может доверять роли из браузера. Go проверяет доступ к каждому объекту.

Текущий каркас не имитирует вход: закрытые адреса перенаправляются на страницу входа, POST входа недоступен. Макеты только под /preview/. Нет сбора паролей, личных данных, загрузки решений и публикации результатов.

## Открытые вопросы

Go API входа/выхода и проверки пользователя; хранение и проверка сеанса; предметные операции; БД и файловое хранилище; серверы и схема размещения. WSGI/ASGI точки входа есть, но промышленное развёртывание не входит в заготовку.
