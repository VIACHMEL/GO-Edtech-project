# Архитектура: исходное предложение

Утверждено: Go backend и Django/Python для представления вместо Rust. Один репозиторий; отдельные процессы Django и Go. Django формирует страницы и обращается к Go через HTTP API. Все правила, проверка личности и прав, предметные данные и миграции принадлежат Go. Выбор БД и хранилища файлов ещё открыт. Основание: decisions/001-django-presentation.md.

## Границы

- backend/: API, права, пользователи/группы, каталог, работы, попытки и проверка.
- frontend/: Django страницы кабинетов, каталог, конструктор, выполнение и проверка; шаблоны, оформление и клиент API Go. Нет предметных ORM-моделей, Django-пользователей, фиктивного входа и доступа к основной БД.
- pipelines/: импорт источника и пакетная обработка SVG/TikZ, включая подготовку данных и эксперименты модели.
- docs/contracts/: общие контракты API и фоновых задач.

Ресурсоёмкую конвертацию выполнять фоново. Она не должна блокировать открытие задания. Отдельный процесс обработки не означает необходимость выделять все модули в микросервисы. Язык обучения модели ещё не выбран; не подменять Go backend другим стеком.

## Потоки

Браузер → Django обработчик страницы → API Go → права и предметные правила → постоянное хранилище → ответ Go → шаблон Django → браузер.

Пока API входа не согласован, закрытые маршруты Django перенаправляют на страницу входа, которая не принимает пароли и не выдаёт личность. Публичные /preview/ содержат только явно обозначенные макеты без личных данных. Роль из URL/cookie не разрешает доступ. Полный механизм входа, выхода и передачи подтверждённой личности требует отдельного контракта.

Локальный /health/ проверяет только процесс Django. /ready/ обращается к явно настроенному health URL Go; без настройки или при сбое возвращает 503. Это не проверка входа или готовности всего MVP.

Школково → адаптер импорта → исходные материалы → нормализованная версия задачи → проверка → каталог.
SVG → исходник → преобразование → TikZ → ограниченная компиляция → сравнение и проверка → опубликованный вариант изображения.
Каталог → версия работы → назначение → попытка → ответы → проверка → подтверждённый результат.

Веб-интерфейс получает готовое отображаемое изображение, а TikZ хранится как исходное описание. Не компилировать TeX заново при каждом просмотре.

## Инварианты

- Опубликованная работа ссылается на конкретные версии задач; новый импорт не меняет уже выданное условие.
- Эталонный ответ не выдаётся клиенту до разрешённого этапа.
- Все операции проверяют доступ пользователя к ученику, группе, работе и вложениям.
- Генерируемые TeX и импортируемые SVG — недоверенные данные. Компиляция без сети, shell escape, доступа к секретам и с лимитами ресурсов; SVG очищается перед отображением.
- Сохранять происхождение, версии преобразователя/модели и статусы обработки.
- Оригинал, оптимизированный SVG, TikZ и превью — отдельные артефакты, связанные ID.
